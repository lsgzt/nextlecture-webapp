# NextLecture Faculty Attendance setup

The faculty attendance portal is a self-contained `/faculty/*` route family inside the existing Vite/React application. It runs on a **completely separate Supabase project — `attendance_record` (`jchoopzbwihjmhkjulfz.supabase.co`)** — with its own Supabase Auth realm, its own tables, and its own RLS policies. The existing NextLecture database, the LMS project, and every student-facing feature are untouched.

## One-time setup

1. **Apply the migration** — open the `attendance_record` project in the Supabase dashboard → SQL Editor → paste the whole of `supabase/faculty-attendance/0001_init.sql` → Run. It is idempotent (safe to re-run) and creates only `public.faculty_*` objects.

2. **Provision the teacher accounts** (server-side, uses the secret key):

   ```bash
   bunx tsx scripts/faculty_attendance_provision.ts
   ```

   Creates the two Supabase Auth users (email + password, `email_confirm: true`) and links their `faculty_teachers` rows. Idempotent — re-running never duplicates users and never resets passwords teachers have already changed (use `FORCE_PASSWORD_RESET=1` to re-issue initial passwords).

3. **Import the roster and timetable**:

   ```bash
   bunx tsx scripts/faculty_attendance_sync.ts
   ```

   Reads the same public sources the app already uses (the official GNDEC timetable + the first-year student directory), matches every active teacher against the timetable, and upserts `faculty_students`, `faculty_teaching_assignments` and `faculty_timetable_slots`. Prints a validation report (missing roll numbers, duplicates, groups without roster) and records it in `faculty_sync_runs`.

4. **Restart / redeploy** the web app so the new `VITE_*` variables are picked up.

## Vercel deployment steps

1. Add the two `VITE_FACULTY_ATTENDANCE_*` variables (Production + Preview) in Project Settings → Environment Variables.
2. Add the three server variables (`FACULTY_ATTENDANCE_SUPABASE_URL`, `FACULTY_ATTENDANCE_SUPABASE_SECRET_KEY`, `FACULTY_SYNC_SECRET`) the same way — Vercel only exposes them to serverless functions, never the client bundle.
3. Deploy (`vercel --prod` or push to the production branch). `pnpm build:vercel` already covers the new files.
4. Rerun the roster sync after any deployment with a fresh timetable:

   ```bash
   curl -X POST https://nextlecture.vercel.app/api/faculty/sync \
        -H "x-faculty-sync-secret: $FACULTY_SYNC_SECRET"
   ```

## How the data model works

- `faculty_teachers.id` **is** the Supabase Auth user id of the `attendance_record` project. The two projects do not share auth users.
- `faculty_students` is an independent copy of the official first-year roster (roll number = university registration number, unique). The source directory is never modified.
- `faculty_teaching_assignments` is the authorization matrix — one row per (teacher, subject, timetable group). It is populated only by the admin sync; teachers cannot self-assign.
- `faculty_timetable_slots` holds each teacher's weekly schedule (composite labels like `CSF1+CSF2` mark jointly-attended lectures).
- `faculty_attendance_sessions` / `faculty_attendance_entries` / `faculty_attendance_audit_log` store submissions. A unique constraint on `(teacher_id, attendance_date, start_time, timetable_group)` prevents duplicate submissions.
- Writes happen **only** through two SECURITY DEFINER functions that re-verify the caller server-side:
  - `faculty_submit_attendance(...)` — atomic (single transaction) session + entries + audit insert, with roster completeness and assignment checks.
  - `faculty_correct_attendance(session, student, status, reason)` — reason ≥ 10 characters required, appends an audit row, updates tallies.
- RLS: teachers can read only their own profile, assignments, slots, sessions, entries and audit rows, and only students whose `timetable_group` matches one of their active assignments. No client-side insert/update/delete paths exist for any table.

## Known limitations

- Until the migration is applied, the portal runs in an auth-only mode: sign-in works against the real project, but pages show sample data with a persistent setup banner.
- If the env variables are missing entirely, the portal falls back to a read-only sample dataset (same pattern as the LMS module).
- Corrections are per-student with a required reason; there is no bulk-edit of submitted registers by design.
